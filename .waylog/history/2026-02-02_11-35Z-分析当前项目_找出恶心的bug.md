**OpenAI Codex**

对的，自动配音流水线基本按你列的顺序执行，不过每一阶段还有些细节：

1. **字幕识别 (Transcribe)**  
   - 调 `SubtitleGenerator`：先 `preprocess_audio` 把整段转成 16 kHz mono 的临时 wav，再 chunk（默认 30 秒）喂给 Qwen3‑ASR。  
   - 每个 chunk 返回的时间戳会被标准化、合成最终的字幕列表 (`start/end/text`) 并写回任务状态。

2. **字幕翻译 (Translate)**  
   - 用 DeepSeek Chat 的批量接口，把所有字幕文本打包成 ~100 行一批，翻成目标语言。  
   - 翻好的文本会存进原字幕结构的 `translated_text` 字段，也作为后续配音的输入。

3. **人声分离 (Audio Separation)**  
   - `DubbingManager` 调 Demucs CLI（`htdemucs --two-stems=vocals`）把整段音轨拆成 `vocals.wav` + `no_vocals.wav`。  
   - 这个步骤只跑一次，产出的伴奏轨会用于最后的混音。

4. **声音克隆 & 目标语音生成**  
   - 对每条字幕行：根据 `start/end` 从 `vocals.wav` 裁出对应的原声片段，作为参考声音。  
   - 把 `translated_text`（或原文作为辅助）连同裁切出的参考片段喂给 Qwen3‑TTS，生成目标语言的语音 clip。  
   - 每个 clip 会带上起止时间，供后面的混音阶段使用。

5. **混音与合成 (Mix & Merge)**  
   - `AudioMixer.mix` 把所有生成的语音 clip 按照字幕的时间戳 overlay 在背景伴奏 `no_vocals.wav` 上，得到新的配音音轨。  
   - 用 ffmpeg 把原视频的视频流和新的音轨重新 mux，生成最终的 dubbed MP4，并顺便导出混合音频（MP3）供单独下载。

所以整体流程正是你理解的“字幕识别→翻译→人声分离→声音克隆→目标语音生成”，最后再加一步把音视频合成输出。每个阶段完成后都会在 `/dubbing/auto/status/<task_id>` 的 `stage/progress` 字段里更新，方便前端显示进度。

**OpenAI Codex**

“Dub” 阶段其实包含三个重量级步骤，所以耗时明显高于前两步：

1. **人声/伴奏分离 (Demucs)**  
   - 把整段原音频送进 Demucs（`htdemucs --two-stems=vocals`），它会跑一个卷积+Transformer 模型把人声、伴奏分开。  
   - 这个模型要处理整条音轨，即便视频只有十几秒，也得加载模型、跑全段推理，所以存在固定开销。

2. **逐字幕行的声音克隆 (Qwen3‑TTS)**  
   - 对每条字幕行：  
     1. 用 ffmpeg 在分离出的 `vocals.wav` 上按 `start/end` 裁出对应的“参考语音”片段。  
     2. 把 `translated_text`、参考音频、原文字幕一起喂给 Qwen3‑TTS，让它克隆原说话人的 timbre/风格，输出目标语言的语音 clip。  
   - 如果视频有 30 行字幕，就要串行执行 30 次裁剪 + 30 次 TTS 前向推理，每次推理还得在 GPU/MPS 上加载上下文、生成语音波形，这部分是最花时间的。

3. **混音与视频合成**  
   - `AudioMixer.mix`：把所有生成的语音 clip 按时间戳 overlay 回分离出的背景伴奏轨，必要时用 ffmpeg `atempo` 做时长校准，再导出完整的“配音音频”。  
   - `merge_video_audio`：再跑一遍 ffmpeg，把原视频的视频流和新音轨 mux 成 MP4。  
   - 同时会复制生成文件到 `outputs/` 并写下载 URL。

因为 3. Dub 要处理整段音频、逐行生成语音、再混音，所以它会长时间保持在 `status: processing` / `stage: dubbing`。如果你想让这个阶段更快，可以考虑：

- 减少字幕行数（合并短句）或缩短视频，直接减少 TTS 次数。
- 在 `DubbingManager` 里把裁剪/TTS 改成并行（例如 `asyncio.gather` + 限制并发），能把多行字幕同时生成。
- 缓存 Demucs、TTS 模型，避免同一会话反复加载。
- 如果只是测试流程，可暂时替换成 dummy TTS（如固定语音），验证 pipeline 后再换真实模型。

目前的实现就是按上述流程串行执行，所以“Dub”阶段看起来会卡比较久。

**OpenAI Codex**

提高 Dub 阶段效率但仍保持时间轴精准，可以从“减少要生成的 clip 数量”“并行或缓存繁重步骤”“优化裁剪/对齐策略”三方面入手：

- **先压缩字幕密度**  
  - 预处理字幕：把相邻、间隔 <0.3 s 的短句先合并为 1 行，保持上下文连贯又能减少 TTS 次数。  
  - 限制最短/最长时长（例如 <0.7 s 的行直接并到前一行，>6 s 的行分段），既平衡自然度，也让时间轴更稳定。

- **并行生成语音 clip**  
  - 目前 `for sub in subtitles` 串行跑裁剪+TTS。可以用 `asyncio.Semaphore(k)` 或 `concurrent.futures.ThreadPoolExecutor` 把裁剪和 TTS 拆成任务（例如一次 3–4 行），并在加入 Mixer 前按 `index` 排序，时间轴仍精确。  
  - 注意 TTS 模型显存，请限制并发数；但即便每次两行，也能把几十段语音的总时间砍半。

- **缓存分离与裁剪输出**  
  - Demucs 的输出 (`vocals.wav`, `no_vocals.wav`) 可以在同一视频重复使用（例如补 dub、不同语言），没必要每次重跑。把它们缓存到 `temp_dubbing/<hash>/`；若文件存在且 hash 匹配直接复用。  
  - 对字幕裁剪的参考片段也可缓存：key = `f"{video_hash}_{start}_{end}"`，只要时间轴没变就不用重新 ffmpeg。

- **精确裁剪 + 自动偏移**  
  - 生成 clip 后，计算 `len(seg)` 与目标窗口的差，若超出阈值（±100 ms），用 `ffmpeg atempo` 或 `librosa.effects.time_stretch` 做轻微伸缩，保证 clip 能严密贴合 `[start,end]`。  
  - Overlay 时用 `final_mix = final_mix.overlay(seg, position=start_ms)`，保持时间轴准确。

- **TTS 级联模式**  
  - 先对整段字幕跑一遍文本到音素/时长预测（某些 TTS 支持 batch inference），再针对每行只做声码器推理，这样感知对齐由模型内部完成，CPU 侧只负责拼接。

- **后台阶段化反馈**  
  - 每完成固定数量的 clip（比如 10%），就更新 `tasks[dub_task_id]["progress"]`，前端可以更细粒度展示，不必依赖 UUID。

组合策略可以是：合并短句→启动并发裁剪+TTS（Semaphore=3）、缓存 Demucs 输出→对生成 clip 做时长校正→一次性混音。这样“精准度”仍由字幕时间戳和裁剪窗口决定，但总耗时会显著下降。

不可以直接把翻译的目标语言直接生成语音，然后再对齐到时间轴上吗

**OpenAI Codex**

理论上可以“先把整段翻译文本直接丢给 TTS，生成一整条目标语音，再想办法贴合原始时间轴”，但实践里有几个硬伤：

- **节奏/停顿不一致**：翻译后的语句长度经常和原文差很多（尤其中 ↔ 英），单纯把整段音频按原字幕的时间块硬切，很容易把一个句子切断或者把停顿切到句中，听感非常突兀。

- **语速无从匹配**：TTS 生成的整段语音通常按模型自己的默认节奏来，缺少“说一句→停顿→下一句”的结构。要再对齐到原字幕时间，必须对每个字幕窗口做时间拉伸/压缩，等同于在每个窗口上再跑一次 time-stretch，声音质量会明显下降。

- **无法做声纹迁移**：我们目前的克隆方案是“参考原句的短 audio + 对应文本”，让模型在那句的语境里模仿说话方式。如果一次性生整段，就失去了逐句参考音频的上下文，很难维持说话人的 timbre 和情绪。

- **对齐误差难纠正**：逐句生成时，我们可以在发现 clip 超长/过短时即时用 `atempo` 调整。而如果整段生成后再劈回原时间轴，偏差是累计的：前面稍微超了几十毫秒，后面就会越来越错位，最终字幕+口型会完全对不上。

当然也有一些折中的方向，比如：
1. 先把翻译结果按字幕行切分（或重新切分成“呼吸友好”的单位），每一行独立做 TTS，再 overlay；这是我们现在的做法。
2. 如果想全段生成，可以在文本里人工插入 `<break time="xyzms">` 之类的 SSML 控制语句，强制 TTS 在每句之间停顿。然后再按照这些停顿点切分音频。但这要求 TTS 支持 SSML，还得确保翻译后插入的停顿和字幕时间一一对应，实操成本不低。
3. 使用能输出音素对齐/时长预测的 TTS（比如 FastSpeech2 + 可控 duration），你可以在模型输入时直接指定每个字/词的 duration 来匹配原字幕窗口。但这就等同于“每行一句”，只是把 duration 约束交给模型而不是后处理。

所以，为了既保留声纹又对齐时间，最好还是“逐字幕行生成 + 按时间戳 overlay”。这能精确控制每一行的入口/出口，必要时还可以对单行做微调，而不是在整段音频上大动刀子。
